01 · What it is

One question in.
A checked answer out.

Nova is a chat app that decides how hard to think. A greeting gets an instant reply. A real task, like comparing two banks, analysing a stock or explaining a clause in your own PDF, goes to a team of specialist agents who gather evidence, compute exact numbers and cite every claim.

Answers

Every claim has a source

Document passages are cited as D1, D2; fetched numbers as Live data. A Sources list shows exactly which file and section each came from.

Transparency

You watch it work

A live, numbered work log streams each step: "Analyst → calculating 12000 × 12", "Reviewer: approved". It folds into one line when the answer lands.

Any task

Not just finance

Code, plans, comparisons, maths, document Q&A and live stock research all route through the same general-purpose team.

02 · Multi-agent architecture

A team, not a prompt.

Each agent is a separate LLM call with its own role, instructions, tools and model. The Planner routes; specialists work in parallel; the Writer drafts; the Reviewer can force one rewrite.

Why three models

Spreading load across free-tier budgets

Groq's free tier gives each model its own budget of ~8,000 tokens per minute. A team run uses 10–15k tokens, too much for one model, so agents are spread across three models with separate budgets.

03 · Retrieval-augmented generation

Grounded in documents,
not memory.

Text is split into section-aware chunks, embedded locally, stored as int8 vectors, and searched with two complementary methods fused by Reciprocal Rank Fusion.

Pipeline 
# indexing
document → chunks 800 chars · 150 overlap · section header
         → BGE-small embeddings 384 dims · local · no API key
         → int8 + base64 4× smaller · ~no quality loss

# every search_documents call
query → BM25 ranking    exact terms: "NPA", "SEBI"
      → vector ranking  meaning: "borrowing" ≈ "debt"
      → RRF: Σ 1/(60 + rank) → top 4 → D1…D4

Serverless functions have no disk, so uploads are indexed by /api/library and stored in the browser, then sent back with each chat. Stateless server, no database.

04 · Tool calling

The model asks.
The code decides.

Tools are described to the model as JSON Schema. It returns a structured request; the server validates it, runs it, and feeds the result back, in a loop, until the agent can answer.

Live data

Market tools

analyze_stock returns quote, 1-year technicals (SMA, RSI, volatility, drawdown), 3 years of financials and news in one compact call, so a full analysis fits the token budget.

Exact maths

A calculator you can't exploit

No eval(). Expressions are parsed with Python's ast and only numbers, operators and whitelisted functions run. __import__("os") is rejected.

Documents

search_documents

Hybrid search over the 60-chunk knowledge library and the user's uploads, with stable D# refs shared across every agent in the run.

05 · Engineering lessons

Bugs that taught the most.

Every one of these was found by testing, diagnosed from the provider's real error messages, and fixed in code rather than with prompt wishes.

empty replies

The model forgot its own reasoning

gpt-oss reasons before calling tools. Dropping that reasoning when sending tool results back made it end turns with no text. Fix: pass the reasoning back with the tool calls.

instant 429s

Rate-limited with zero usage

Groq reserves max_tokens against the per-minute budget up front, and one model's default exceeded 8,000 alone. Fix: explicit per-agent max_tokens.

lost data

A crashed agent threw away its work

A model called a tool after being told not to; Groq rejected the call and all fetched bank data vanished. Fix: a notes fallback so gathered data is never lost.

72 s, failed → 19 s, complete
over-eager agent

Searching for what isn't there

The Researcher searched the library 7 times for company news it doesn't hold. Fix: tell it what the library contains, and cap search rounds in code.

37 s → 9.3 s
json mode

Reasoning ate the reply

The Reviewer's hidden reasoning used its whole token allowance before writing JSON. Fix: low reasoning effort for JSON agents, and a reviewer failure now skips the review instead of crashing.

formatting

Never trust a model's brackets

Citations arrived as 【D1】 and with zero-width spaces inside. Fix: normalise the stream in code; validate, don't assume.

06 · Safety & security

Public, but protected.

A security review shaped the backend before any agent was added.

Abuse

Rate limits & lockout

20 messages and 10 uploads per minute per IP; 5 wrong access codes lock an IP out for 15 minutes. Codes compared with secrets.compare_digest.

Injection

Nothing renders raw

Every model reply is HTML-escaped before Markdown is applied; links are limited to http(s). Visitors can't send system messages.

Inputs

Validated at the edge

4 MB uploads, zip-bomb checks on Word files, ticker regexes, Pydantic size limits on library payloads, keys kept out of git and the browser.

07 · How it was built

From one API call to an agent team.

  1. step 1

    A terminal chatbot

    First Groq call, a system prompt, conversation memory and token streaming in chatbot.py.

  2. step 2

    A web app on Vercel

    FastAPI backend, a hand-written streaming UI, Markdown rendering, light and dark themes, PDF and Word uploads.

  3. step 3

    Security hardening

    Access code, per-IP rate limiting, timing-safe comparisons and input limits, from a full security review.

  4. step 4

    Tool calling

    Live market-data tools with a streaming tool loop, plus the reasoning and token-budget fixes that made it reliable.

  5. step 5

    RAG: Ask My Docs

    A standalone RAG pipeline with BM25, embeddings, RRF, a reranker and an evaluation harness.

  6. step 6

    The agent team

    Planner, Analyst, Researcher, Writer and Reviewer on three models; RAG over a knowledge library and user uploads; a safe calculator.

  7. step 7

    Design pass

    An interface audit that removed glows and looping motion, and added a numbered work log and source tags.
