1. What you built

Nova is a chat assistant on the web (FastAPI backend on Vercel, plain HTML/JS frontend). This project added three abilities:

AbilityWhat it means in Nova
Tool callingThe model can ask the server to run Python functions: an exact calculator, live data lookups (market data today; web search when a key is set) and document search.
RAGNova searches a built-in knowledge library (7 reference documents, 60 chunks) and the user's own uploads on any topic (reports, notes, manuals), and cites the exact passage: [D1].
Multi-agentFor any substantial task, a Planner decides who works on it: an Analyst (live data, calculations) and/or a Researcher (documents) in parallel; a Writer produces the answer, report, plan or code; a Reviewer checks it and can force one rewrite.

The team is general-purpose. Some examples of how the Planner routes work:

RequestTeam
"hey, how's it going?"Direct: no team needed
"Write a function that validates IPv4 addresses"Writer + Reviewer (Reviewer checks the code for bugs)
"I save 12,000 a month at 7%: how much after 5 years?"Analyst (exact calculation) + Writer + Reviewer
"From my report: why did margins fall?"Researcher (searches your document) + Writer + Reviewer
"Compare two companies and explain the key metrics"Analyst (live data) + Researcher (library) in parallel + Writer + Reviewer
One sentence for your CV: Built a general-purpose multi-agent assistant (planner, tool-using analyst and researcher, writer, reviewer) with hybrid-search RAG over a knowledge library and user documents, live-data and calculator tools, and streamed agent traces, running entirely on free-tier APIs.

2. Key ideas in one page

  • An LLM can't do anything by itself. It only produces text. "Tool calling" means the text it produces is a structured request (get_stock_quote(symbol="TCS.NS")) that your code runs.
  • An agent is a loop: the model thinks, calls a tool, reads the result, and decides what to do next, until it can answer.
  • RAG (Retrieval-Augmented Generation) means: find the relevant passages first, put them in the prompt, then ask the model to answer only from them and cite them. It reduces made-up facts and lets the model use documents it was never trained on.
  • Multi-agent means splitting one job between several LLM calls, each with a narrow role, its own instructions and its own tools. Narrow roles are easier for a model to do well.
  • Everything costs tokens. On Groq's free tier each model allows about 8,000 tokens per minute. Most design decisions in this project come from that budget.

3. Tool calling

3.1 Describing a tool to the model

You send the model a list of tools as JSON Schema: a name, a description (the model reads this to decide when to use it), and the parameters.

{"type": "function", "function": {
  "name": "get_stock_quote",
  "description": "Current price, valuation (P/E, P/B, market cap), 52-week range ...",
  "parameters": {"type": "object",
                 "properties": {"symbol": {"type": "string"}},
                 "required": ["symbol"]}}}

3.2 The loop

# simplified from agents.run_specialist
messages = [system, user_question]
for round in range(MAX_ROUNDS):
    reply = groq.chat.completions.create(model, messages, tools=TOOLS)
    if not reply.tool_calls:               # plain answer: done
        return reply.content
    messages.append(reply)                 # remember what it asked for
    for call in reply.tool_calls:          # run each tool in Python
        result = run_tool(call.name, call.arguments)
        messages.append({"role": "tool", "tool_call_id": call.id, "content": result})

The model never touches the internet. It only asks; your code decides whether and how to run the request. That's also a security boundary: stock_tools.py validates every ticker with a regular expression before it reaches Yahoo Finance, and tool errors go back to the model as {"error": ...} so it can correct itself (for example, look up the right ticker and retry).

3.3 Designing good tools

  • Return compact JSON. Every character you return is read by the model and counts against the token budget. The tools drop empty fields and trim long text.
  • Combine tools that are always used together. analyze_stock returns quote + trend + financials + news in one call. Before it existed, a full analysis took 5 rounds (each resending the whole conversation) and blew the 8,000-token budget; now it takes 2.
  • Write descriptions for the model, not for humans. "Use this whenever you are not sure of the exact symbol" changes behaviour.

4. What makes it "agentic"

There is a spectrum, and it helps to name the levels:

LevelWho decides the steps?In Nova
ChatbotNobody: one call, one answerThe original chatbot.py
Tool-using agentThe model, inside a loopNova with the Agent team switched off
WorkflowYour code: fixed stepsSpecialists → Writer → Reviewer order is fixed
Multi-agentA planner model routes work to other agentsThe Planner chooses direct vs research and which specialists to use
Design principle: give the model freedom where it adds value (which tools, which searches, which specialists) and keep fixed code where reliability matters (always Reviewer after Writer, a hard time budget, at most one revision). Fully free-form agents are impressive in demos but hard to debug and expensive.

The Analyst's safe calculator

LLMs are unreliable at arithmetic, so the Analyst has a calculate tool. The obvious implementation, eval(expression), would be a serious security hole: the expression is written by a model that may have read text from a user or a web page, and eval runs any Python, e.g. __import__("os").system(...). Instead, agents.calculate parses the expression into a syntax tree with ast.parse and evaluates only numbers, arithmetic operators and a whitelist of maths functions; anything else is rejected, and huge exponents are blocked.

calculate("12000 * ((1 + 0.07/12)**60 - 1) / (0.07/12)")   # → {"result": 859114.819777}
calculate('__import__("os")')                              # → {"error": "only numbers, + - * / ..."}

Why "notes" instead of raw tool output?

Specialists summarise what they found into short notes. The Writer reads ~400 words of notes instead of thousands of characters of JSON. This is context compression, and it's why a five-agent run fits in the free tier.

Structured outputs

The Planner and Reviewer must answer in JSON (response_format={"type": "json_object"}) so code can read their decisions. Code then validates them: unknown agents are dropped, a "revise" verdict without issues is treated as "approve", and any failure falls back to safe behaviour (the Planner falls back to normal Nova; a failed Reviewer just skips the review).

6. Why each agent uses a different model

Groq's free tier gives each model its own 8,000 tokens-per-minute budget. A team run uses roughly 10,000–15,000 tokens in total, which is too much for one model in one minute. Spread across three models it fits:

ModelAgentsStrength
qwen/qwen3.8-27bPlanner, ResearcherFast, good at JSON and short tool loops
openai/gpt-oss-120bAnalyst, ReviewerStrongest reasoning: numbers and fact-checking
openai/gpt-oss-20bWriter (and normal Nova)Fast streaming prose

The models are set in agents.MODELS and can be changed with environment variables (PLANNER_MODEL, ANALYST_MODEL, RESEARCHER_MODEL, REVIEWER_MODEL).

Watch out: Groq counts max_tokens against the per-minute budget before running the call. Every agent therefore sets an explicit, small max_tokens (see section 12).

7. RAG inside Nova

Nova's RAG (nova-web/rag.py) is a web-friendly version of your Ask My Docs project (rag/). The concepts are the same; read the RAG learning guide for the deep dive.

INDEXING                                   SEARCHING (each search_documents call)
knowledge/*.md ─┐                          query ──► BM25 ranking   ─┐
user uploads  ──┴► chunks (800 chars,              ──► vector ranking ─┴► RRF ─► top 4 passages
                   150 overlap, section header)                          numbered D1, D2...
                ──► BGE-small embeddings (384 numbers)
                ──► int8 + base64 (1 byte per number)

7.1 The built-in knowledge library

nova-web/knowledge/ holds 7 Markdown documents: valuation ratios, technical indicators, financial statements, the Indian market (NSE/BSE, SEBI, trading hours, taxes), earnings and news, risk basics, and sector metrics. python build_index.py chunks and embeds them into knowledge_index.json (60 chunks, 58 KB), which is committed. The deployed app only loads that file; it never re-embeds the library.

7.2 Hybrid search with Reciprocal Rank Fusion

BM25 matches exact words (great for "NPA", "SEBI", tickers); vectors match meaning ("borrowing" ≈ "debt"). Their scores are on different scales, so RRF ignores the scores and adds 1 / (60 + rank) from each list. A passage ranked well by both wins.

7.3 Quantisation: int8 vectors

An embedding is 384 floats (4 bytes each = 1,536 bytes). Because BGE vectors are normalised, every number is between −1 and 1, so we store round(x × 127) as one signed byte: 384 bytes, 4× smaller, with almost no loss in search quality. Vector databases use the same trick.

def pack_vec(vec):
    q = np.clip(np.round(vec * 127), -127, 127).astype(np.int8)
    return base64.b64encode(q.tobytes()).decode("ascii")

7.4 Graceful degradation

Embeddings run locally with fastembed (free, no API key). If the model can't load (no disk space, package missing, NOVA_EMBEDDINGS=off), rag.embedder() returns None and search silently becomes BM25-only. Nova gets a bit less smart but never breaks.

7.5 Citations end to end

Each search result gets a stable ref (D1, D2...) stored in the run, so the same passage keeps the same number across searches. The Writer cites refs; after the answer, code appends a Sources list containing only the refs the answer actually used, with file, section and whether it came from the library or the user's document.

8. Your documents in a serverless app

A Vercel function has no permanent disk: it can be shut down at any moment, and the next request may run on a different machine. So where do uploaded documents live?

  1. The browser sends the file to POST /api/library.
  2. The server extracts text (PDF up to 300 pages, Word, text), chunks it, embeds each chunk, and returns the chunks with their int8 vectors.
  3. The browser stores them in localStorage (key nova-library-v1), max 20 documents / 400 chunks.
  4. Every chat request includes the library; the Researcher's search_documents tool searches it together with the built-in library.

Trade-offs: requests get bigger (a full library is a few hundred KB, well under Vercel's 4.5 MB limit), and the library lives in one browser. A production system would use a vector database (pgvector, Qdrant, Upstash Vector) keyed by user account.

Long attachments are added automatically: a file longer than 15,000 characters used to be cut off; now the first part goes into the message and the whole document goes into the library, where the Researcher can search all of it.

9. Evaluating retrieval

python eval_rag.py runs 16 hand-written questions (knowledge_eval.json), each labelled with the section that answers it. Hit@4 = how often that section is in the top 4 (what the agent actually reads). MRR = average of 1/rank of the first correct result.

MethodHit@4MRR
BM25 only88%0.73
Vector only88%0.81
Hybrid (RRF)94%0.77

BM25 missed "golden cross" phrased as "50 day average crosses above the 200 day average" (different words), and vector search missed "comparing companies with different amounts of borrowing" (it found debt ratios instead of EV/EBITDA). Each method fails on different questions, so combining them catches more. The remaining miss ("warning signs in a company's accounts" vs the section titled "Red flags") is a vocabulary gap that a reranker or query rewriting could fix.

16 self-written questions is a regression check, not a benchmark. Its value is telling you whether a change (chunk size, model, new documents) made things better or worse.

10. Streaming the agents to the browser

Everything travels in one plain-text HTTP stream. Three control characters, which never appear in normal text, carry the agent trace:

MarkerMeaningBrowser does
\x02label\x03Status: "Researcher → searching documents: NPA"Adds a chip above the reply
\x04The Reviewer requested a revisionClears the draft; the revised answer streams in its place
anything elseAnswer textRenders it as Markdown

Specialists run in background threads and push events into a queue.Queue; the HTTP generator reads the queue and yields text. That's how parallel agents can report progress through a single stream.

The heart of the pipeline (agents.research, simplified)

with ThreadPoolExecutor() as pool:                       # 1. specialists in parallel
    futures = {t["agent"]: pool.submit(run_specialist, run, t["agent"], t["task"])
               for t in tasks}
findings = {a: f.result() for a, f in futures.items()}

notes = notes_block(question, findings)
draft = stream_writer(run, writer_model, system, history, notes)   # 2. draft, streamed

review = critique(run, notes, draft)                     # 3. check
if review["verdict"] == "revise" and run.time_left() > 12:
    run.events.put(("reset", None))                      # 4. replace the draft
    stream_writer(run, ..., notes + draft + review["issues"])

Safety rails in code (not in prompts)

  • Time budget: 48 seconds per run (Vercel stops at 60). The Reviewer and revision are skipped if time is short; specialists stop calling tools when under 24 s remain.
  • At most 4 tool rounds per specialist, one revision per answer.
  • Rate limits: waits up to 20 s once, then tells the user to try again.
  • Input limits: the library and messages are validated by Pydantic models (sizes, counts).

12. Problems we hit (real engineering lessons)

1. Empty replies after tool calls. gpt-oss models reason privately before calling a tool. We dropped that reasoning when sending the tool results back, so the model lost its train of thought and ended its turn with no text. Fix: send the reasoning back with the assistant's tool-call message. Lesson: read the model provider's docs on multi-turn tool use; models differ.
2. Calls refused instantly with "rate limit". No tokens had been used, yet qwen calls failed in 0.2 s. Groq counts prompt + max_tokens against the per-minute budget before running a call, and qwen's default max_tokens alone exceeded 8,000. Fix: explicit MAX_TOKENS per agent. Lesson: when an error appears instantly, it's a policy check, not a workload problem. Print the provider's real error message.
3. The Reviewer's JSON failed to validate. gpt-oss-120b spent its whole 600-token allowance on hidden reasoning and never wrote the JSON. Fix: reasoning_effort="low" for the Planner and Reviewer and a larger allowance. Also: a failed Reviewer now just skips the review instead of crashing the answer. Lesson: reasoning tokens count toward max_tokens; and optional steps must fail safely.
4. Wrong citation formats. The Writer wrote 【D1】 (full-width brackets) and sometimes hid zero-width spaces inside citations, so the Sources list missed them. Fix: normalise the stream in code. Lesson: never rely on a model's exact formatting; normalise and validate.
5. Market data cited as D1. Both specialists were told "cite passages as [D1]", so the Analyst numbered its own data and the Writer mixed them up. Fix: a separate notes format per agent, with [Live data] for one and [D#] only for document passages. Lesson: in multi-agent systems, shared instructions leak into the wrong roles. Give each agent only the rules it needs.
6. A crashed specialist threw away its data. On the Analyst's last round we sent tool_choice="none", but the model called a tool anyway and Groq rejected the request, so all the bank data it had fetched was lost and the answer said "no market data". The run also took 72 s, past Vercel's 60 s limit, because the analyst fetched one tool per round. Fix: the final round sends a plain "write your notes now" message with no tools offered; if that fails, the raw results become the notes. Specialists stop gathering when 24 s remain, every Groq call has a 20 s timeout, and the analyst is told to call analyze_stock for all companies in one parallel turn. Lesson: design every step so a failure degrades the answer instead of destroying work already done.
7. An over-eager agent and a leaking rule. After the team became general-purpose, two things went wrong. For "Analyse TCS" the Researcher searched the library 7 times for company news it doesn't contain, taking 37 s and leaving no time for the Reviewer. And a savings-plan answer ended with the stock disclaimer. Fix: tell the Researcher what the library does and doesn't hold, tell the Planner which agent owns company data, cap the Researcher at 2 search rounds in code, and limit the stock rules to actual stock analyses. Lesson: agents keep trying when they can't find something; give them a stopping rule and a hard limit. And scope every special-case instruction narrowly, or it spreads to unrelated tasks.
8. Free-tier budget shapes the architecture. One model with five tool rounds ran out of tokens. Combining tools (analyze_stock), compressing results into notes, and spreading agents across models with separate budgets made it fit. Lesson: cost and rate limits are design inputs, not afterthoughts.

14. Limitations and next steps

  • No reranker on the web. The cross-encoder from rag/ would improve accuracy but adds another ~80 MB model. Next step: add it locally or use an LLM to rerank the top 10.
  • Library lives in one browser. Next: user accounts plus a vector database.
  • Free-tier ceiling: about one team task per minute. A paid tier or caching repeated lookups would raise it.
  • No answer-quality evaluation yet. Retrieval is measured, but final answers aren't. Next: a small set of questions scored by an LLM judge for faithfulness to the notes.
  • Predictions remain uncertain. The outlook is a structured opinion with Low/Medium confidence, not a forecast. This is research, not financial advice.

15. Interview questions (with answers)

What is tool calling and who executes the tool?
The model outputs a structured request (name + JSON arguments) matching a schema you provided. Your application validates and runs it, then sends the result back as a "tool" message. The model never executes anything itself.
When would you use multiple agents instead of one?
When sub-tasks need different instructions, tools or models, can run in parallel, or benefit from independent checking (a reviewer). The costs are more tokens, more latency and harder debugging, so cheap questions should skip the team, which is what Nova's Planner does.
How do you stop agents looping forever or running up costs?
Hard limits in code: max tool rounds, one revision, a wall-clock budget, explicit max_tokens, and a planner that routes simple questions to a single call.
How does your RAG reduce hallucinations?
Specialists report only what tools and passages returned, the Writer must cite every claim, and a Reviewer checks the draft against the notes and can force a rewrite.
Why hybrid search?
BM25 catches exact terms and codes; embeddings catch paraphrases. In our evaluation each alone reached 88% Hit@4 and hybrid reached 94%, because they fail on different questions.
How did you handle user documents on a serverless platform?
The server indexes and returns int8-quantised chunks; the browser stores them and sends them with each request. Stateless server, no database, at the cost of larger requests. In production I'd use a vector DB per user.
Tell me about a hard bug.
Instant 429 errors with no usage: Groq reserves max_tokens against the per-minute budget up front, and one model's default was larger than the budget. Logging the provider's real message found it; explicit per-agent max_tokens fixed it.
